# Oct-Incs/Mods

このリポジトリは **ゲームMOD開発専用** です。それ以外の用途(一般的なアプリ開発等)
には使いません。

## リポジトリの構成

ゲームごとにトップレベルフォルダを分け、その中に各MODを1フォルダずつ格納します:

```
<GameName>/<ModName>/
```

現在の内容:

| ゲーム | MOD | パス | 概要 |
|---|---|---|---|
| RimWorld | JP_Beasts (和ノ獣譚) | `RimWorld/JP_Beasts/` | 妖怪・古代獣・古代昆虫を追加する野生動物コンテンツMOD |

新しいMODを追加する場合は、対象ゲーム名のフォルダ(無ければ新規作成)の下に
MOD名のフォルダを作り、そのMOD専用の `README.md`(ユーザー向け説明)と、
ある程度以上の規模になったら `HANDOFF.md`(開発引き継ぎ資料 — 後述)を
用意すること。

## 後継セッションへ: 作業を始める前に必ずすること

1. **どのMODについての依頼か確認する。** 複数ゲーム・複数MODがこのリポジトリに
   混在し得る。ユーザーの依頼がどのゲーム/どのMODを指しているか曖昧な場合は、
   憶測で作業を始めず、まずユーザーに確認すること(このリポジトリが元々
   1MODしか無かった時代に、別リポジトリだと思い込んで見当違いの調査を
   進めてしまった事故が実際に起きている)。
2. **対象MODのフォルダ直下にある `HANDOFF.md` を必ず読む。** 存在する場合、
   その MOD の開発方針・過去に発生した不具合と解決策・現在の設計判断の根拠が
   まとまっている。同じ調査をゼロからやり直さないために必須。
   (例: `RimWorld/JP_Beasts/HANDOFF.md`)
3. **`main` ブランチが常に最新の完成形。** 作業は `main` から新しいブランチを
   切って行い、完了したら `main` にマージすること。過去に、ある1つのMODの
   実装が長期間フィーチャーブランチにのみ存在し `main` にマージされておらず、
   別の新規セッションが `main` から新しいブランチを切った結果そのMODの存在に
   気づけない、という事故が起きている。作業が一区切りついたら `main` への
   マージを怠らないこと。
4. **もしこのリポジトリが `Notion-reader` という1ファイルしか無い空の状態に
   見えたら、それはこのリポジトリの実際の状態ではなく、古い/誤ったチェック
   アウトを見ている可能性が高い。** 実際に過去2回、後継セッションが
   「`main`にはコミットが1件(`Create Notion-reader`)しかなく、MODの中身が
   一切無い」と報告する事故が起きているが、その都度 `git fetch origin main`
   で最新の`main`を取得し直すと(あるいは新規に `git clone` し直すと)
   きちんと `RimWorld/JP_Beasts/` 以下の内容が存在することを確認できている
   ("Notion-reader" しか無いのは、このリポジトリが作られた最初期・一番古い
   状態そのものであり、そのセッションのチェックアウトが更新されずに
   固定されてしまっていたことが原因と判明している)。**「空に見える」と
   感じたら、結論を出す前に必ず `git fetch origin main && git log
   origin/main --oneline -5` で最新コミットハッシュを確認すること。**
   それでも空であれば初めて本当に何か問題がある。
5. このリポジトリの実際の名前は **`Oct-Incs/Mods`**。過去に `Oct-Incs/i` という
   名前だった(現在はリネーム済みで `Oct-Incs/i` へのアクセスは自動的に
   `Oct-Incs/Mods` にリダイレクトされる)。セッションの認可スコープが古い名前
   (`oct-incs/i`)のまま残っている場合、git remote の URL は
   `https://github.com/Oct-Incs/i` のままで問題なく動作する
   (プッシュ時に「moved」という警告が出るだけで、実際には正しいリポジトリに
   届く)。逆に remote URL を新名称 `Oct-Incs/Mods` に変更すると、
   セッションの認可スコープと一致せず **push が 403 で失敗する** ことを
   確認済み。git remote の URL を新名称に変更しないこと。
